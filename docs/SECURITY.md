# Security

## Trust model

gozler's index holds every file name, and the daemon shows each user only the names that user may see. Stated plainly:

- The daemon runs **elevated** and builds its index from a raw NTFS MFT read, or on ReFS from a folder walk with backup semantics, which both bypass per-file ACLs. The index therefore contains the name, size, and timestamps of every file on every tracked volume, regardless of who can normally read them. The daemon filters what it shows each user, as the next points say.
- The query pipe (`\\.\pipe\gozler-v1`) grants **Authenticated Users** read/write, so any authenticated local user can query the index. It exposes only metadata, never file contents, and it answers each user for that user: a search shows only the entries in folders the user's token may list, which are the names File Explorer shows that user, including the names of files they cannot open. Every count, total and export adds only those entries, and a folder has a size only for a user who sees every file, because a folder's size would show how much a hidden file holds.
- A user sees every name only when the user, or a group the user's token holds enabled, is on the list of users and groups who see every file, or when the request runs as SYSTEM. An administrator is no exception, elevated or not, and a restricted token never sees every name. The list is the value `SeeEveryFile` of `HKLM\SOFTWARE\Gozler`: every user may read it, and only administrators and Local System may write it, because a user who could change it could turn the filter off for themselves. On a first install, the setup offers the signed-in user a place on the list, with the box checked, and shows the choice before the install stores it; adding Everyone turns the filter off for every user.
- The client opens the pipe at the identification level, so the daemon can read which user and groups a request comes from, but neither the daemon nor a program that took the pipe name can act as that user. The daemon refuses searches from a client that connects anonymously, because serving it as nobody would give empty answers that look like "no such file", and serving it everything would let any program bypass the filter.
- Conversely, the client verifies the pipe server's owner SID is Local System or the built-in Administrators group before sending anything, and fails closed. A non-elevated process cannot squat the pipe name and impersonate the daemon, and never gets a token for the user, because the client sends nothing before it has checked the pipe's owner. The `--insecure-no-server-check` flag opts out of that check and is a development escape hatch only.
- The Include page's preview count, `CountIncluded`, answers only a user who sees every file: its folder and name rules cover the whole index, so any other user could count hidden entries one pattern at a time until the counts spell their names.
- Two things are not hidden. How long a search takes shows roughly how many entries a hidden folder holds, and the daemon does not pad its answers, because padding would slow every search. On a domain that uses central access policies, the folder's own descriptor decides, so the daemon's answer can differ from File Explorer's.
- The service log is readable by every user, so it names no file or folder: it counts the folders whose permissions could not be read, and `gozler --status` shows that count.
- A result snapshot, the rows of a search that the daemon keeps for later reads, is read by its id, 128 random bits that only the client that made it learns over its own pipe. Each read of it shows a row only to a user who may see it, as a search does. The daemon reads each client process's user SID only to cap how many result snapshots one user keeps, so one user's searches cannot fill the daemon's memory at another's expense beyond the cap on all of them.
- The Include settings, which decide what the index holds, are a value in `HKLM\SOFTWARE\Gozler`, which only administrators and Local System can write, and so is the token that asks for a rebuild of the index. Any user may send `SettingsSaved`, because the daemon then applies only what an administrator saved and rebuilds only for a token an administrator wrote, so the pipe needs no check of who sends it.

## Reporting a vulnerability

Please report security issues privately rather than opening a public issue, using GitHub's [private vulnerability reporting](https://github.com/SynoSoftware/goz/security/advisories/new) (the "Report a vulnerability" button under the repository's Security tab). You will get an acknowledgement, and a fix or mitigation plan once the report is confirmed.
