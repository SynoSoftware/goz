Do gozler-ui's patterns fit its job?

module seam leak across a seam deep module

Verdict. The patterns fit what the window does today: one search list over millions of entries, a service behind a pipe, one modeless progress window. Native Win32, a core that decides and is tested on any OS, Rc window state with window rule 1, request slots with generations, and an owner-data list with a chunk cache are what a careful Windows desktop engineer would choose.

Four seams in app and in the update protocol still assume one list and one window. Each is cheapest to decide in Stage 3's restructuring, before features build on it.

Problem. Stage 3 splits the list state in core, but MainWindow stays one dispatcher with one list built in. Three lists through it put a list id into every handler and triple the scattered fields.

Solution. One controller module per list view, the established Win32 pattern: it owns its control wrapper, its column sizing and drag-over state, its notification handlers and its link to its list state. A panel may also be a child window with its own window procedure, which lets two panels reuse control ids.

  • Leverage: one controller, three lists
  • Locality: list behaviour leaves MainWindow
  • Explains first report's candidates 2, 6, 8, 10
  • Grilled candidate 2's column sizing lives here

Grilled · 2 rounds · frontier empty · stays Strong

  • What the controller owns: the list control and its message area, which is created before the list so that it comes first in the Tab order. Also the column-sizing state, drag_in, selection_pending, and its SEARCH, SELECTION and DROP_SCROLL timers.
  • What the window keeps: fonts, metrics, image lists, icons, numbers, the window-drag flag, the taken set and the OLE drop registration. These reach each call as one value of shared resources.
  • A struct, not a child window: events are matched by window handle (ControlEvent::is), and Tab is decided by commands::tab_stop. So nothing forces a child window. Panel controls are children of the main window, hidden on a mode switch, as FilterPane::placed_with already does.
  • Model access: the controller holds no Rc. Its methods take &RefCell<Model>. They return an Outcome: Apply(Accepted), Start(Fetch), Run(CommandId), DragOut or None. The window acts on it after every borrow has ended, so window rule 1 holds.
  • One type plus composition, no trait. A panel's list switches kind while it runs: Alt+F7 makes it a search panel, and Esc makes it a folder panel again. So the differences go in a per-list kind in core: where rows come from, how selection works, how taken rows look, bold parts, how the row is drawn. The parts only a panel has go in a Panel struct that contains one controller.
  • Depth: about 18 methods hide about 650 to 730 lines of today's main_window.rs. The deletion test passes: without the controller, three lists would add three copies of each field to MainWindow, and a ListId to every handler.
  • Timers: each list timer gets a base well clear of the window's ids 1 to 7, plus ListId. One timer::list decodes them. Switching to Search kills the panels' timers and cancels their requests, as the spec's "ask gozlerd nothing" requires.
  • Activation: Model::activate(ListId) → Accepted, saved through candidate 4's compare. It is triggered only by gaining focus, never by losing it: NM_SETFOCUS (which needs a new ListNotify variant), the path box, the panel search box, and explicit calls from the drive button, the status line and Alt+F1 or Alt+F2. A control key goes to the controller that owns the key's target window. A command goes to the active list.
  • Model::failure is the service's fact. It is renamed, and stays window-wide. A status reply that answers again gives a SearchAgain for each list that shows a recoverable failure.
  • P3 does not block P1. Both options need show_states and the control keys that move only the focus. Option (a) adds a capture_states call. Decide P3 before Stage 4.
  • Order: P2's reshape, then candidate 2's core::columns, then the extraction (a plain move), then "Two lists in Layout::compute".
  • Not unit-tested: routing by window handle, which review and the Stage 4 screenshots cover. Also the loop that re-applies a panel's selection, which is checked once in the running window in Stage 4.

P2. Let one accepted change carry several effects, each naming its list

core/model.rs — Accepted { change, then: Option<Then> }, Then::ReadSelectionSoon, set_selection's or_else · app/main_window.rs — apply

Before

Accepted { change, then: Option<Then> }
Then::ReadSelectionSoon = cancel Selection + start a timer, bundled into one variant
set_selection picks one effect; correct only because a new fetch of a purpose cancels the old one
Ctrl+U, an operation's end, a panel search: one action, effects on two lists

After

Accepted { change, then: Vec<Then> }
each Change and list-bound Then names its list; apply runs the effects in order

Problem. One effect slot forces combined variants and implicit cancel rules, and nothing names a list.

Solution. A list of effects (as Elm's Cmd.batch), with a list id on what concerns one list.

Meets the grilling of candidate 1. That grilling chose one Then::FileOperations(Steps) variant so as not to change Accepted for every subsystem. If P2 is taken, Steps becomes ordinary entries in the list. Decide P2 first.

Found while grilling. apply runs accepted.then before accepted.change. Then::ConfirmSetup and Then::ExplainNoSetup open dialogs, so the person answers a setup question before the same reply's status change shows. This is inferred from the code, not run.

Under P2, put the dialog in a field of its own, Accepted { change, effects, dialog: Option<Dialog> }. The type then allows at most one dialog, and apply runs it last.

Grilled · 2 rounds · frontier empty

  • When: in Stage 3's restructuring. Stage 3 already edits most Fetch and Cancel sites and every list arm. The reshape touches 21 Change variants, 11 Then variants and 80 places that build an Accepted, all of them in model.rs, plus 28 model tests that change mechanically.
  • Shape: changes: Vec<Change>, only for independent facts. Today's code already folds two changes into one in accept_status and set_taken. A plain Vec is enough: hot paths build at most two effects, and an empty Vec does not allocate.
  • Order inside apply: changes, then effects, then the footer, then the last slot. No current Then has to run before its change shows. fetch_visible even needs its change applied first. update_status moves to the footer.
  • Naming the list: a ListId (Search, Left, Right) goes on each variant that concerns one list. Fetch and Cancel name the list through Purpose. An effect resolves "the active list" to a fixed list when the change is accepted, so a Tab within the 150 ms delay cannot redirect a search or a selection read.
  • Cancels: "one live request per purpose" stays the documented rule of the request slots (window rule 4). set_selection's or_else goes.
  • Other return types: the five request methods keep returning a bare Fetch, because they change only request bookkeeping. enter_in_search_box returns Accepted, and SearchBoxEnter goes.
  • Effects hidden in change arms move out: the NewSearch arm runs release_ended and fetch_visible. It also opens the first row, and Open can show a modal box from inside that arm.
  • Defect: T2 and T3 send no selection cancel. DESIGN requires one. The indirect chain does not provide it: accept_results and show_failure set Selection::None first, so the later set_selection sees no older read to cancel. A selection read of up to 100,000 rows (about 25 pages) runs on until the next selection or Exit. Found by reading, not reproduced.
  • Late cancels, not missing ones: the Results branches that show a message (a parse error, a missing folder, Type to search, a failure) cancel only when the next search starts.
  • A queue that apply drains: it replaces the nested apply calls. A nested Accepted is appended to the queue. Each Accepted runs whole, its changes and then its effects, before the next one starts. The footer runs once.
    • No synchronous Win32 path reaches apply today, apart from direct calls that move out.
    • The queue's rules live in core, with callbacks, so tests can reach them.
  • Modal steps: an ordered Vec<Modal> runs after the footer.
    • It is a list because one wake can carry an export failure and a setup question.
    • Each step runs with draining off, so replies show behind the dialog, as T10 requires.
    • Each step asks the model again whether it still applies before it runs.
    • Every reply of a wake is accepted before any dialog opens. Today a dialog inside the drain loop can show replies out of order (found by reading).
  • An Effects type: it holds at most one request step for each purpose, and the last one pushed wins. No legitimate sequence needs a cancel after a fetch of the same purpose. One proptest covers the rule.
  • Tests:
    • T2 and T3 send their cancel.
    • The message branches cancel the Results request.
    • The Effects proptest.
    • enter_in_search_box's three outcomes.
    • A status failure returns both of its changes.
    • The queue: a nested Accepted runs after the outer one, the footer runs once, and the modal steps run in order with draining off.
  • Independent review: the direction holds, with gaps.
    • The footer can be re-entered. update_inspector makes a shell call that can dispatch messages. A reply accepted during that call is appended to the queue after the queue looked empty, so it never shows, and the list can stall in "Searching…". Rule: drain until the queue is empty, and run the footer again if it refilled.
    • Every deferred step must name its purpose. The "last request per purpose wins" rule must count SearchSoon, SearchAgain and the selection timer as requests. Otherwise [SearchSoon, Cancel(Results)] still starts the search.

    • ListId lands with the per-list state, not with the first reshape.
    • Strength: P2 should be Strong, because the T2 and T3 fix depends on it.

P3. Folder panels: say who owns the selection when the disk changes

docs/plans/file-manager-spec.md — "Selecting entries", "The list follows the disk" · DESIGN "The selection"

The spec says both

"The list owns which rows are selected, as in Search"

each disk change applies by name; "The focus and the selection stay on the same names"

An owner-data list view keeps selection by index. A row inserted above the selection moves it to other files unless code maps it by name and sets it again. Search avoids this by striking rows through instead of removing them.

Two ways

a. The list owns the selection; around each applied change, the panel reads the selected names, applies the change, and sets LVIS_SELECTED from those names.

b. The panel's state owns the selected names (Total Commander and Far keep their own marks); LVIS_SELECTED is set from them, and Ctrl-click, Shift-click and Ctrl+A still go through the list.

Problem. Without a decision, Stage 4 adds a second owner of the selection under time pressure.

Solution. Decide a or b in the spec before Stage 4; Stage 4's test "the selection keeps its names" then has one owner to test.

Problem. DialogBoxParamW, MessageBoxW and menu loops dispatch other windows' messages without our routing. Settings is modal over the main window only, so the File operations window stays enabled while Settings is open, and its Tab, Enter and Esc lose dialog handling. A Viewer's own keys would stop the same way.

Solution. Route keys where every loop reaches them: each window's procedure, or a WH_MSGFILTER hook. Run the window once to confirm before acting.

Problem. Each route was invented locally. The plan adds at least five more thread kinds: folder reading, folder watching, drive labels, free space, the Viewer's reads.

P6. One way to hold saved state

Today the window keeps saved state two ways: some values are live in Settings (Model::sort() returns settings.window.sort), and others are copied in at save time (save_settings(path, placement, columns)). Per-list sorts and panel folders need one way. The grilling of candidate 4 already picked it: Settings is the live store, and the window saves when it differs from the last saved copy. Columns and placement move into it.

Recorded reasons that no longer hold as written (verified)

  • DESIGN's "Shared code" table says "core makes no filesystem call", but core::settings::Settings::load and save call std::fs::read_to_string, write and rename.
  • DESIGN rejects "a list of commands that one applier runs" because it "cannot answer LVN_GETDISPINFO". The window does run such a list (Then, through apply) and answers LVN_GETDISPINFO with a short read borrow. The reason that holds is that the controls own selection and scroll, so a diffed copy would duplicate that state.
  • DESIGN's "Not planned" says a second window does not fit because "one window serves a session". The File operations window, the "Allow only one Gozler window at a time" setting and the scheduled Viewer contradict it. The same list puts Rename and drag-out under Not planned, while "Dragging" describes drag-out as built and the spec schedules Rename.
  • DESIGN says win holds every unsafe block; src/timing.rs (test-only) has 9.

Settled choices, not re-argued

Native Win32 through the windows crate and native controls; .rc dialog templates; the native list renderer; the 100,000-row limit and no result snapshot yet; sizes and totals from gozlerd; no shell context menu; no old protocols; no Recycle Bin; the window never lags; only the window is translated, with JSON catalogues; Start of words by default; Tab reaches only the search box and results; one window per session by default; Use local points at the gozlerd.exe beside the window; menu icons, disabled-not-hidden buttons and the text rulings.

Top recommendation

P1 with P2: a controller per list, and effects that name their list

Stage 3 is next, and its "one state for each list" splits core only. Deciding the matching seams in app and in Accepted in the same restructuring costs the least rework; every later stage builds on them.
