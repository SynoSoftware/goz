Problem. To run one search, a caller must know a long interface: three lock holds in a fixed order, which volumes each page locks, the per-volume limit offset + limit, how to add the sums, and that the scope folder must be resolved under the same lock as the scan. stream_rows, run_query, a proptest and deep_export.rs each write this sequence again.

Solution. A core module takes the compiled query, the scope path, the sort and the rows request, and returns pages or totals. It reaches each volume through a lock-window seam, as index::settle::SharedIndex already does. gozlerd becomes one adapter that locks in VolumeSet order, plus the page encoder.

  • Locality: each search rule gets one owner
  • Leverage: one interface for gozlerd, benches, examples
  • Two adapters make the seam real
  • Golden corpus can run on Ubuntu CI
  • Visibility threads SeenBy in one place
  • Result snapshot stays inside core

Evidence: the find_matches doc states the three-hold rule. server.rs computes per_vol_limit and maps IndexChanged. server/tests/corpus.rs is in the daemon, and the daemon's modules are #[cfg(windows)]. docs/DESIGN.md ("Rows on demand") already says that the daemon should only take the locks and send the pages.

Grilling outcome: settled
  • ResultRows<V> in query/rows.rs: ResultRows::search and query::search_totals. The answer owns its volumes. The page call locks, fills one page, releases the locks, and only then returns.
  • Trait IndexedVolume: a read guard (HeldVolume, which gives the index, whether the phase is complete, and metadata_pending, from one call), plus the mounts. Two adapters: Arc<VolumeState> and a plain index. SharedIndex stays separate.
  • Coverage is read once, during the scan, as today. Reading it on every page would mark rows from a complete index as incomplete.
  • query does not import proto. proto converts Rows and encodes the frame in one function, which replaces the closure in stream_rows and the copy in deep_export.rs.
  • Errors: NotIndexed for rows; NotIndexed | Overflow for totals. The corpus moves to core and runs on Ubuntu.

Problem. Three functions do this check with five pub(crate) index accessors. Scan::evaluate copies the no-path rule from Reply. Its comment says so, "so the two cannot drift". find_head mixes the check with the total, the offset skip and the merge. Reply cannot seek: rows store no sort keys, and the merge reads the current values. A skipped offset row costs the same as a sent row.

Solution. The index answers one question with a typed verdict: which file is this row now, or why is it gone. The query module adds the scope check and the visibility check once. Reply and a result snapshot reader are two callers of that check, with different outcomes.

  • Locality: one owner for each row rule
  • Interface shrinks: five accessors become one verdict
  • Tests assert verdicts, not page output
  • Visibility adds one check, not two
The result snapshot plan's "Not measured" section says a read of 16,384 rows "reads its rows as a page does today, without the scan". With today's Reply, a read at a far offset also walks every earlier row under the locks (Reply::fill counts rows "sent or skipped for the offset"). The plan's time estimate does not count that walk.
Grilling outcome: downgraded; do it with visibility stage 2 or the result snapshot
  • The reuse-mark check in read_rows stays. SortRecord is asserted to be 16 bytes and has no room for a file ID. Scan::evaluate already shares in_scope and entry_folder. The page-time check has one caller today.
  • The page-time check becomes an Option<FolderId>, not a four-case enum, because neither caller handles the reasons differently.
  • Only past_cut changes in VolumeRows during a reply. If it moves into the reader, the rows can be shared by a snapshot.
  • A snapshot jumps to an offset by storing the merged order: 1 byte per row, plus a marker every 4,096 rows (about 6 % more memory). It holds its volumes through Weak, and checks them with Arc::ptr_eq against the current VolumeSet.

Problem. tail_loop mixes journal I/O with every retry, degrade, escalate and rescan decision. No test reaches the decisions, because the loop needs a real VolumeHandle.

Solution. A pure state machine takes a classified read outcome and the time, and returns the next action. The loop keeps only the I/O. supervisor::assess already works this way.

  • Tests reach the real policy
  • Locality: each rescan trigger in one table
  • Follows an existing pattern in the crate
  • Rebuild index stays outside the rescan budget
Grilling outcome: Speculative; only while Rebuild index edits the loop
  • It fails the deletion test: one caller, about 30 lines, and no defect in the policy. If it is done, only ReadFailures becomes a type, with now: Instant. Four tests replace retry_policy_is_bounded_and_degrades.
  • Rebuild index is a rescan that does not count against the rescan budget. A rules change and a rebuild request share one "next build" value, which begin_build clears, so two requests that arrive together cause one build. The request goes through the supervisor.

Problem. Include is written for one registry value. The service settings plan and the visibility plan each add a separate way to save and read a setting, in different registry keys. The visibility plan states the conflict itself. Each new piece of daemon-wide state is passed through four functions and five test calls of serve.

Solution. One daemon module owns the saved service settings: it reads them, checks them, reloads them on SettingsSaved, and tells the parts that use them. Include becomes one section. The pipe server receives one context.

  • Locality: one reload path
  • Two adapters: registry and test fake
  • New setting changes one module
The visibility plan reads its value on every request on purpose, so that it needs no notification code. If one module already sends a notification for each change, that reason no longer applies. Decide this before stage 1 of the visibility plan.
Grilling outcome: dropped; one placement decision remains
  • The two registry keys stay, each for its own reason: uninstall drops the visibility list on purpose. The list keeps its read on every search. A settings module that held both would share nothing.
  • Dates created becomes a field of the existing Include value: one administrator save and the same way to apply a change.   • The context struct comes with ViewRegistry, not before. A dc: search while Dates created is off is refused, with a message that names the setting.

Defects found while grilling

Both were found by reading the code. Neither was run. A separate session is fixing both now (see Status).

Changed Include settings never reach a volume without a journal thread

Fleet::apply_settings only calls set_rules, which sets a flag. Only tail_loop reads that flag (take_new_rules). A snapshot volume and a volume the supervisor gave up on have no journal thread. So if you uncheck a folder on such a volume, gozler still finds its entries until gozlerd restarts. Leaving out a whole volume works, because reconcile handles it. The fix: the supervisor starts a journal thread for such a volume, and that thread's first build reads the current rules. Rebuild index and Dates created use the same route.

The window's sums can be larger than the result count

match_sums runs once, during the scan. The page total then drops for each row that read_rows and find_head leave out, but the sums do not drop. docs/DESIGN.md says that the totals "agree with the result count". The difference is only the rows that changed between the scan and their page.

Owner decisions: settled
