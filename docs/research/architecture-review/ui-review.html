Where it stands. The crate's three-way split holds: core decides, win holds the unsafe, app turns messages into calls. Model with Accepted, the command table, the request slots and the results cache are deep and tested. Problem. The rules that decide what is asked next, which ended delete or move stays alive to keep its rows struck through, when a cut paste counts as moved, and when the window opens or polls live in a struct that creates a window, so none of them is tested. The shutdown order is enforced by a mem::forget in a different module.

Solution. A core module in the Accepted/Then style takes queue snapshots and list events and returns actions. The window becomes an adapter that runs them. The module that owns the Queue owns its shutdown in one method.

  • Stage 3's taken-set rules get unit tests
  • Locality: one owner for taken entries
  • Delete four RefCell fields from the window
  • Shutdown order leaves the caller's interface

Evidence: the spec's Stage 3 says the queue's taken set splits and asks for core unit tests such as "an ended delete still hiding its rows until a listing started after its end arrives". The current interface cannot host those tests. Reasons that still hold: the conflict question runs its own message loop (window rule 1); dropping the queue waits for every Windows copy.

Grilled · 4 rounds · frontier empty · stays Strong

  • Scope: this is how Stage 3's "Taken entries split" item gets built, not a separate plan. The same seam serves Stage 5, where the end of a Rename or a New folder makes a panel read its folder again.
  • Who owns what: app keeps the Queue, because the queue exists only on Windows. core reads Operation snapshots. Each list owns the ended operations it keeps. The queue's set holds only waiting and running sources. Today kept holds two facts. "Already reported" belongs to the lifecycle; "kept" belongs to the lists.
  • Interface: it is part of Model, as a private field like Fixer. It adds file_operation_started(id, source), accept_operations(&[Operation]) → Accepted, answered(id, Answer) → Accepted and Change::Taken for each list. The dialogs follow confirm_setup's steps.
  • Several effects: one snapshot can need several effects, and Accepted.then holds one. If pattern P2 is taken, they become ordinary effects in a list. "At most one dialog, run last" is then a type: an Option<Dialog> field.
  • Wakes: the engine wakes only on state changes, never on progress. The lifecycle runs on each wake and never on the 500 ms poll. With P5, the wake becomes one QueueChanged event in the window's channel.
  • Shutdown: ManuallyDrop<Queue> inside the type that owns the queue replaces the caller's mem::forget. Dropping the queue would cancel CopyFile2 and delete partly copied files.
  • Engine: gozler-fileops gets a public OperationId constructor and a public way to build a taken set. The engine spec's "Taken entries" text changes with them.
  • Tests: Stage 3's listed cases, plus:
    • a question is asked once;
    • an ended delete or move is kept only when it took something;
    • each ended operation is reported once;
    • a cut paste counts as moved only once its move was accepted;
    • every drop gets exactly one ending.
  • Vocabulary: "taken" stays out of CONTEXT.md. It is a word of the code and the plans; the person sees a struck-through row.

Grilled · 2 rounds · frontier empty · stays Strong

  • How saving is decided: Model keeps a copy of the settings as last saved. Each change compares the settings with that copy and starts the save timer when they differ. A new method cannot forget to save.
  • Failed saves: the copy is taken when a save is attempted, so a failing disk is not written after every keystroke.
  • Columns: toggle_column and a new reorder method keep the shown columns current in Settings, in display order. The reorder arrives through HDN_ENDDRAG and is read in Message::Deferred.
  • Placement: it is recorded on WM_WINDOWPOSCHANGED, the one message that covers maximize, restore, snap and Win+Arrow. It uses its own small compare-and-save step, not apply.

  • Settings Apply: it runs all four refreshes inside one draw_once_after. Whether it flickers is unverified until the window runs once.
  • Commits: first a restructuring with no behaviour change, then three fixes. The Saving-defects row in the defects table lists them.
  • DESIGN is the authority here: it says ui.json is "written a second after the person last changed the window's state" and lists placement and column order. These fixes match it, so they are not owner questions.

Independent review: the comparison is right; three corrections.

  • The save can be postponed for a long time. Once a change is pending, every apply restarts the 1-second timer: export progress about twice a second, chunks and selection replies. During an export, a change is then saved only when the export ends. Start the timer only when the settings changed since the previous check. Keep the last-saved copy only for the SAVE handler's skip.
  • One draw_once_after does not draw once. It does not nest, and refresh_text wraps itself in its own. Apply all four state changes first, then call refresh_text once.
  • Snap adds nothing to save. GetWindowPlacement reports a snapped window's restore rectangle. WM_WINDOWPOSCHANGED is still the right message.
  • Open question: recording the placement must start at the first show. Otherwise a window that starts hidden in the tray could replace a saved maximized placement before it ever shows.

Independent review of candidates 1, 3, 7, 8 and 9

A reviewer that wrote none of this work checked these candidates. It kept their strengths, except that candidate 7 rises to Strong. Its corrections:

  • C1: create the File operations window only when it is first needed. #98 measured 75 ms of the 627 ms startup in creating that window. The show and hide rules then stay with the lifecycle (C8).
  • C1: a quick move ends before its first snapshot. A move within one drive can finish before the lifecycle sees it waiting or running. The lifecycle then never sees it "waiting or running", so the clipboard keeps the cut files and Paste stays enabled. Instead, return the result of submit to core.
  • C1: build each operation's taken set on the engine's prepare thread, and pass it in the snapshot as Arc<Taken>. That keeps 100,000 path folds off the window thread. It also closes a race between operations() and taken() that can show deleted rows for a moment.
  • C1: remove an ended operation from the queue as soon as the lifecycle sees it. Its "reported" memory and the remove rule then go. The main window must close the queue's waker in WM_DESTROY.
  • C3: forget the stored count on each edit, not only cancel the count in flight. Otherwise an old number shows during the 300 ms delay.
  • C7 rises to Strong, because visibility stage 3 adds a second setting saved as administrator ("Users and groups who see every file"), and that stage starts at once. Build the typed Apply outcome for every setting saved as administrator. The 64 is better exposed as Count::MAX by the engine.
  • C8: compute the common folder off the window thread. It takes 272 ms for 100,000 sources, as measured in window-responsiveness.md. Also, the last taskbar state sent belongs in the display value (#93).
  • C9: retry a timeout a bounded number of times, then cache it. Never caching it would restart a slow gozlerd.exe after every 2-second status poll.
  • Defects:
    • The stale Include count shows only briefly.
    • "Offered before the queue opens" is practically unreachable: Queue::new cannot fail; only creating the window can. It folds into C1.
    • The timeout cache also hides the service's version in Settings > Index.
